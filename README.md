# Jetson DLA Energy Predictor

> 碩士論文：**深度學習加速器能耗預測之特徵工程與跨模型泛化研究**
> 國立中正大學資訊工程研究所（2025/08 ~ 2026/07）

在模型真正部署到邊緣裝置**之前**，就根據模型結構預估它在 NVIDIA Jetson AGX Orin 的 **DLA（Deep Learning Accelerator）** 上執行的推論能耗。

邊緣裝置的電力與散熱都有限，部署 AI 模型時除了準確率與速度，也需要事先知道能耗。本研究建立一套區塊（Block）級的能耗預測框架，並驗證它面對沒看過的區塊與模型時的泛化能力。

## 重點成果

| 項目 | 結果 |
| --- | --- |
| CPU 背景功耗預測 | **R² 0.986**、MAE 0.31 W |
| 重複量測的能耗標籤波動（最大標準差 / 平均值） | **四種模型皆 < 5%** |
| 加入硬體執行特徵後的未見區塊誤差 | **SMAPE 下降 23% ~ 66.5%** |
| 未見區塊預測（四種 CNN，各自訓練） | **平均 SMAPE 9.9%、R² 0.97** |
| 跨模型混合訓練（投票集成） | **SMAPE 9.73%、R² 0.964** |

> SMAPE：預測值與實際值相差的百分比，越低越好。R²：越接近 1 代表預測越準。

## 系統架構

```
                 ┌──────────────── PowerProfiler（資料擷取）────────────────┐
ONNX 模型 ──▶ 區塊切分（4 種粒度 A→D）──▶ TensorRT / DLA 推論
(VGG16, VGG19,              │                 │ 同步記錄功耗（INA3221）與執行日誌
 ResNet50, MobileNetV2)     │                 ▼
                            │           依區塊時間區間切分能耗
                            │                 │
                            │   CPU 功耗預測器 ─┤ 扣除 CPU 背景功耗 ★
                            │                 ▼
                            │           DLA 淨能耗標籤
                 └──────────┼──────────────────────────────────────────────┘
                            ▼
                 ┌──────────────── PowerPredictor（預測建模）───────────────┐
                 │  特徵工程 ★：運算量 + 記憶體存取 + I/O 大小 + GPU Fallback │
                 │  預測器：XGBoost、LightGBM、ExtraTrees、投票集成          │
                 │  泛化驗證 ★：LOBO（未見區塊）、LOMO（未見模型）           │
                 └──────────────────────────────────────────────────────────┘
                                                      ★ 本研究的關鍵設計
```

## 方法

### Step 1｜CPU 背景功耗補償：讓能耗標籤變乾淨

INA3221 量到的電軌功耗同時包含 CPU 與 DLA，CPU 的背景負載會成為標籤雜訊。

AGX Orin 的 12 核 CPU 分成三個叢集、頻率各自不同，因此以**三個叢集各自的使用率與即時頻率**作為特徵，用 Ridge Regression 預測 CPU 背景功耗，再從電軌功耗中扣除：

  ```
  DLA 能耗 = 電軌能耗 − CPU 預測功耗
  ```

CPU 功耗預測結果：**R² 0.986、MAE 0.31 W**。

扣除 CPU 背景功耗後，對同一個 Block 重複量測，標籤波動（最大標準差占平均值的比例）都控制在 5% 以內：

| 模型 | 標籤波動 |
| --- | --- |
| VGG16 | 4.36% |
| VGG19 | 4.82% |
| ResNet50 | 4.79% |
| MobileNetV2 | 4.96% |

標籤穩定後，預測器的誤差才能反映模型本身，而不是量測雜訊。

### Step 2｜特徵工程：只看運算量不夠

兩個 MACs 相近的 Block，若其中一個需要搬移更多資料，實際能耗就會明顯較高，只看運算量無法區分。因此在運算量之外，加入與硬體實際執行相關的特徵：

| 特徵 | 說明 |
| --- | --- |
| 運算量 | MACs、FLOPs |
| 記憶體存取 ★ | Memory proxy，估計資料搬移量 |
| 資料大小 ★ | Input / Output tensor size |
| GPU Fallback ★ | DLA 不支援、退回 GPU 執行的 Layer 比例 |

特徵從 ONNX 模型結構與 TensorRT 建置日誌中萃取（例如 Layer Fusion、Compute Density）。加入新特徵後，各模型最佳預測器在未見區塊上的 **SMAPE 下降 23% ~ 66.5%**。

### Step 3｜三層泛化驗證

一般的隨機切分會讓同一個 Block 的資料同時出現在訓練與測試集，等於看過答案。本研究採用更嚴格的留一法，並分成三層，難度逐層提高。

**第一層：同模型未見區塊（LOBO, Leave-One-Block-Out）**

每次把一整個 Block 拿出來當測試，其餘 Block 用於訓練。

| 模型 | SMAPE | R² |
| --- | --- | --- |
| VGG16 | 12.74% | 0.96 |
| VGG19 | 8.92% | 0.98 |
| ResNet50 | 8.81% | 0.97 |
| MobileNetV2 | 9.15% | 0.97 |
| **平均** | **9.9%** | **0.97** |

**第二層：四種模型混合訓練，一個預測器通用**

四種 CNN 的資料一起訓練，同樣以 LOBO 預測未見區塊。

| 預測器 | 平均 SMAPE |
| --- | --- |
| XGBoost | 19.22% |
| LightGBM | 9.81% |
| ExtraTrees | 10.46% |
| **投票集成（Voting）** | **9.73%** |
| 堆疊集成（Stacking） | 23.67% |

投票集成最穩定（R² 0.964），與各模型分開訓練的 9.9% 相當；堆疊集成反而最差，集成方法並非越複雜越好。

**第三層：完全沒看過的模型（LOMO, Leave-One-Model-Out）**

整個模型都不給預測器看。下表每一列為要預測的模型，每一欄為訓練資料來源（平均 SMAPE，粗體為最佳訓練來源）：

| 預測 ＼ 訓練 | VGG16 | VGG19 | ResNet50 | MobileNetV2 | 其餘三模型 |
| --- | --- | --- | --- | --- | --- |
| VGG16 | — | 32.5 | 56.2 | 58.8 | **26.1** |
| VGG19 | **24.0** | — | 69.8 | 67.8 | 27.7 |
| ResNet50 | 81.0 | 91.7 | — | **48.4** | 79.7 |
| MobileNetV2 | 82.9 | 90.7 | **34.4** | — | 57.0 |

- 架構相近的模型之間遷移效果最好：VGG16 ↔ VGG19、ResNet50 ↔ MobileNetV2。
- 架構差異大時，誤差超過 80%。
- 用其餘三個模型一起訓練不一定比較好（例如 VGG19：只用 VGG16 訓練為 24.0%，三模型一起為 27.7%），**訓練資料的結構「像不像」比資料「多不多」更重要**。

## 實驗環境

| 項目 | 內容 |
| --- | --- |
| 硬體平台 | NVIDIA Jetson AGX Orin（12 核 CPU，三叢集） |
| 功耗量測 | 板載 INA3221 電軌感測器 |
| 推論引擎 | TensorRT（DLA） |
| 測試模型 | VGG16、VGG19、ResNet50、MobileNetV2（ONNX） |
| 區塊切分 | 4 種粒度（Preset A 最粗：完整複合結構 → Preset D 最細：單一運算子） |
| 建模工具 | Python、scikit-learn、XGBoost、LightGBM |

## 限制與未來方向

- 目前只在同一個 Jetson DLA 平台、四種 CNN 上驗證；面對架構差異很大的模型，泛化能力仍有限制。
- 未來希望加入更多種類的神經網路與硬體執行資訊，提升對未知架構的泛化能力。
- 進一步可整合到 Edge AI 部署流程：開發者比較不同模型或配置時，先預測能耗，再依「低功耗優先」或「效能優先」提供部署建議。
